# 学習記録簿 要件定義・設計まとめ（v2.21.18）

## なぜこれが必要か

自分が「何を」・「どれだけ」やったのか可視化するため
やったことに対しどのくらい身についているのかを再確認するため

今までスプシでガントチャート作成と Notion で可視化していたが、見づらさを感じたため

将来的には AI を入れて、これから取り組むことにどのくらいの時間(期間)がかかるかを予測できるようにしていきたい

## 概要

タスク（チケット）単位で学習を管理し、進捗・学習時間を可視化する Web アプリケーション。
タスクは **親タスク（グループ）** / **子タスク（実作業）** / **孫タスク（ステップ）** の 3 階層で管理する。
フロントエンドは HTML/CSS/バニラ JS、バックエンドは Node.js（Express）、データベースは MySQL で構成するフルスタック構成。

> **本文書の反映範囲について**：本文書は v2.21.14 を土台に、直近セッションで対応した v2.21.17（ステップからの実績日自動算出）・v2.21.18（期間内タスク判定基準の統一）の差分のみを追記したものです。実装コード側には`v2.21.15`（サマリーカードのフェードイン演出）・`v2.21.16`（Chart.js の destroy/recreate 廃止・upsertChart 化）に相当するコメントが既に入っていますが、その間のドキュメント差分は本セッションでは把握できていないため、該当箇所は「変更なし」表記のまま据え置いています。次回整理時に反映してください。

### ① ダッシュボード画面

#### ヘッダー：今週の目標表示（v2.18.0 追加）

（v2.21.10 から変更なし）

#### サマリーカード（4 枚）

| カード         | 表示内容                                                                                          | サブテキスト                                                         |
| -------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 期間の学習時間 | 期間トグル（週/月/年/全）と連動した学習時間（時間単位・小数点 1 桁）                              | 先週比 / 先月比 / 前年比 ±N 時間（全期間時は「全データの通算」固定） |
| 進捗率         | 期間内タスクベースの完了率（%）。算出方法は v2.21.13 で見直し（下記「進捗率の集計ロジック」参照） | 先週比 / 先月比 / 前年比 ±N%（全期間時は「全データの通算」固定）     |
| 進行中タスク   | 期間内の「進行中」ステータスのタスク数（v2.11.0：旧「完了タスク」カードから変更）                 | 完了 N / 全 N 件                                                     |
| 読了書籍       | `completed_count >= total_chapters` かつ `total_chapters > 0` の書籍数                            | 読了 / 全 N 冊                                                       |

- 各カードはアイコン付きヘッダー、大きな数値表示、サブテキストの 3 段構成。
- 数値表示は**カウントアップ＋フェードインアニメーション**（v2.21.14 追加）：`animateSummaryValue()`が`requestAnimationFrame`で ease-out cubic のイージングをかけながら 0 から最終値まで遷移させ、同時に CSS クラス（`summary-value-anim--visible`）でフェードインを行う。トグル切替等で短時間に連続更新された場合は、`animId`カウンタで古いアニメーションを自動中断する。

##### サマリーカードのスタイル（v2.9.0 追加）

静的モックアップ（`learning-management-mockup.html`）のデザインに合わせ、見た目のみを変更した経緯がある（カードの構成・件数・データロジックは不変）。

| カード                         | アイコン                     | 色クラス                                           |
| ------------------------------ | ---------------------------- | -------------------------------------------------- |
| 期間の学習時間                 | `clock`（時計）              | `.ic-indigo`                                       |
| 進捗率                         | `trending-up`（折れ線）      | `.ic-amber`                                        |
| 進行中タスク（旧・完了タスク） | `check-circle`（チェック円） | `.ic-green`                                        |
| 読了書籍                       | `book`（本）                 | `.ic-indigo`（`violet`は新設せず`indigo`を再利用） |

- アイコンを囲むボックスは`.icon`クラス（36×36px・`border-radius: 10px`・`display: grid; place-items: center`）
- サブテキスト内の数値部分のみ`.sub-highlight`クラスで緑色（`var(--color-status-done)`）・太字にする。対象は「期間の学習時間」の先週比等の数値、「進捗率」の完了数、「読了書籍」の読了数。「進行中タスク」のサブテキストはハイライト対象の数値がモックに存在しないため対象外（後の v2.11.0 で完了数がハイライト対象に追加された）
- サブテキストの更新方法は`textContent`ではなく`innerHTML`（`<span class="sub-highlight">`を含むテンプレートリテラル）を使用する。これらの値はすべてアプリ内部で計算した数値（ユーザー自由入力ではない）のため、`innerHTML`使用による XSS リスクは許容範囲とする方針が確立している。

#### 学習時間グラフ（画面中部）

グラフレイアウトは「学習時間」セクションと「進捗」セクションに分割し、それぞれにセクション見出し（`.dashboard-section-title`）を表示する（B 案：セクション分割方式）。

- **学習時間セクション（2 カラム）**
  - **日別学習時間**：週表示時は月〜日の棒グラフ、月表示時は日付ごと、年表示時は月別、全期間表示時は年別に切り替わる。予定時間（薄アンバー）と実績時間（インディゴのグラデーション）を並べた 2 系列の棒グラフ。単位は時間（h）。
  - **カテゴリ別学習時間**：`category_name`でグループ化し`study_time`を合計した棒グラフ。期間切り替えと連動。色は GitHub 言語色マッピング（`GITHUB_LANGUAGE_COLORS`）優先、該当がなければカテゴリ名の文字列ハッシュから`CHART_COLORS`パレット（8 色）の色を割り当てる（`getCategoryChartColor()`、`tasks.js`で定義しダッシュボード・リザルト双方から共通利用）。タスク数 0 件のカテゴリはグラフに表示しない。

#### 進捗状況（画面下部）

- **進捗率推移**（折れ線グラフ、全幅）：期間内の予定進捗（%オレンジ線）と実績進捗（%インディゴの塗りつぶし線）を表示。母数の考え方は v2.21.12 で「期間内タスクのみ」に変更（詳細は後述）。ラベル日付は週 → 各曜日 23:59:59、月 → 各日 23:59:59、年 → 各月末 23:59:59、全 → 最古年 1 月〜現在月の各月末 23:59:59。
- **進捗セクション（3 カラム `.charts-row--triple`）**：
  - **ステータス別件数**：未着手・進行中・完了のドーナツグラフ
  - **書籍別進捗率**：タスク数が 1 件以上ある書籍のみ、`completed_count / task_count`を横棒グラフ（0〜100%）で表示。書籍タイトルに含まれる言語名から色を推定（JavaScript/TypeScript/HTML&CSS/React/Java/Python は個別マッピング、それ以外はタイトル文字列ハッシュ）。件数に応じて高さを動的計算（`books-wrapper-js`の height = `Math.max(件数×barHeight, 250)px`、6 件超なら`barHeight=32`、以下なら`45`）。
  - **カテゴリ別進捗率**：タスク数が 1 件以上あるカテゴリのみ、完了率を横棒グラフ（0〜100%）で表示。高さの動的計算は書籍別進捗率と同様（最低 200px、`barHeight`基準は同じ）。
    グラフ軸のテキストカラーは`#aaa`（X 軸ラベル）／`#eee`（Y 軸ラベル・横棒）、グリッド線は`rgba(255, 255, 255, 0.1)`で統一する。

#### 期間切り替え

- 週/月/年/全の 4 トグルボタン（選択状態は`localStorage`の`dashboardPeriod`キーに永続化。GitHub Issue #42 対応・v2.12.1 でリロード時に「週」へ戻ってしまう不具合を修正し、保存キーから復元するようにした）
- 前へ／次へボタンで`viewDate`を期間単位でシフト（週：±7 日、月：±1 ヶ月、年：±1 年）。「全期間」選択時、および現在の期間を表示中は「次へ」ボタンを無効化。表示位置（`viewDate`）自体は永続化の対象外で、リロード時は常に現在日時を起点とする。
- 期間ラベル（例：`7/6 〜 7/12`）を中央に表示。
- 「全期間」選択時（v2.12.0 で正式追加）：日別学習時間グラフのタイトルは「年別学習時間」に変化しラベルは実データの存在年を昇順抽出、進捗率推移グラフは最古年 1 月から現在月まで月単位ラベルで累積カーブを描画、サマリーカードのサブテキストは「全データの通算」固定文字列になる。

#### Chart.js インスタンス管理（v2.21.15〜16）

- 従来の`destroy()`→`new Chart()`という再生成パターンをやめ、`upsertChart(existingChart, canvasEl, config)`ヘルパーに統一。既存インスタンスがあれば`data.labels`/`data.datasets`のみ差し替えて`update()`を呼び、値が「現在値 → 新しい値」へなめらかに遷移するアニメーションを実現する。
- 初回生成時以外は`options`に一切触れない（`Chart.helpers.merge()`による options 手動マージは、Chart.js 内部の Proxy ベース resolver を破壊するバグの原因になるため使用しない、というのが確立した方針）。
- 対象は`chartDaily`・`chartStatus`・`chartBooks`・`chartCategoryTime`・`chartCategoryProgress`・`chartProgress`の 6 インスタンス。共通のアニメーション設定`CHART_ANIMATION = { duration: 700, easing: "easeOutQuart" }`を使用。

#### 進捗率関連ロジックの見直し（v2.21.12：進捗率推移グラフ／v2.21.13：進捗率カード）

進捗率カード・進捗率推移グラフはともに「母数を何にするか」を巡って段階的に見直しを行った。最終的に両者は同じ考え方（期間内タスクのみを母数とする）に統一されている。

- **v2.16.0 で明文化された旧ロジック（v2.21.7 より前）**：進捗率カードの分母は全タスク数（`allTasks.length`、期間フィルタなし）。分子は「選択期間の今日と同じ日付・同じ時刻時点」までに完了したタスク数で、基準日時（`borderDate`）＝選択期間の年・月 × 今日の日・時・分から算出していた（例：2026 年 6 月を選択中・今日が 28 日 14:00 なら、`2026-06-28 14:00`以前に完了したタスクを集計）。前期比も同様に、週なら`borderDate - 7日`、月なら 1 ヶ月前の同日、年なら 1 年前の同日の基準日時点で算出していた。
- **v2.21.7（旧ロジック・現在は上書き）**：進捗率カードは「全タスクのうち、締め日時（`borderDate`）までに完了しているものの割合」という累積の完了率だった。締め日時の算出バグを v2.21.7 で修正したが、母数が常に「全タスク」である点自体は変わっていなかった。
- **v2.21.12（進捗率推移グラフの母数変更）**：進捗率推移グラフは、従来は母数が常に「全タスク」（`allTasks`）だったため、週や月の初日であっても既に全体の進捗率（例：69%）がそのままグラフの開始値になってしまい、「その期間の進捗が 0%からどう積み上がったか」が見えない状態だった。母数を「その期間に属するタスクのみ」（`filteredTasks`）に変更し、期間の開始時点は 0%からスタートして、期間内で完了・予定消化が進むごとに上昇する見た目に変更した。「全期間」トグル時は`filteredTasks`が全タスクと一致するため、従来通りの全体累積進捗と同じ結果になる（挙動は変わらない）。
- **v2.21.13（進捗率カードの母数変更）**：進捗率カードは、v2.21.12 で変更した進捗率推移グラフと考え方がズレており、同じダッシュボード画面内でカードの数値とグラフの数値が一致しないことがあった。進捗率推移グラフと同じ考え方に統一し、母数を「全タスク」から「期間内タスク（`filteredTasks`）のみ」に変更した。週/月/年トグル時は「その期間に属するタスクのうち完了しているものの割合」を表示する。これに伴い、締め日時（`borderDate`）を用いた累積完了率の算出は行わなくなった。「全期間」表示時は`filteredTasks`が全タスクと一致するため、従来通り全体に対する進捗率と同じ値になる（挙動は変わらない）。
- 先週比／先月比／前年比の比較対象（`prevProgressRate`）も同様に、表示中の期間の 1 つ前の期間（`getPeriodRange(currentPeriod, prevBaseDate)`で算出した期間）に属するタスクのうち完了しているものの割合に変更した。締め日時（`prevBorderDate`）によるキャップ処理は行わなくなった。

### ② タスク一覧画面

登録された学習タスクを、カンバン・テーブル・カレンダー・タイムラインの 4 ビューに切り替えて管理する画面。画面上部にビュー切り替えタブ（`.view-tab`）があり、選択中のビューは`localStorage`の`taskView`キーに永続化される。

#### 2.1 カンバン表示

- 「未着手 / 進行中 / 完了」の 3 カラム構成。各カラムヘッダーにステータスドット・件数バッジ・親タスク追加（＋）ボタンを表示。
- 親タスクは`calcStatus(groupId, tasks)`によりステータスを自動判定して該当カラムに表示（`calcStatus`のロジック自体は v2.3.0 で確立）：
  - 子タスクが 0 件 → 未着手
  - 全子タスクが「未着手」→ 未着手
  - 全子タスクが「今年中に完了済み」（`end_date`の年が現在年）→ 完了
  - それ以外（進行中あり・ステータス混在・過去年完了分を含む）→ 進行中
  - 完了列は当年完了分のみにスコープし、過去年に完了した子タスクを含む親グループは進行中列に表示される点に注意
- 親タスクは`group-card`として、タイトル・進捗バー（子タスク完了率、`calcGroupProgress()`、v2.10.0 追加。子タスク 0 件の場合はバー非表示で「－」）・編集ボタンをヘッダーに表示し、クリックで子タスク一覧の開閉をトグル。開いた状態で「＋子タスク追加」ボタンと各子タスクの`task-card`を表示。
- `task-card`には種別バッジ・カテゴリバッジ（「(言語不問)」含め常時表示）・タイトル・期日（開始/終了予定日いずれか）・予定/実績学習時間・ステップ達成度バッジ（`n/m`、v2.15.1 以前から存在）・**ステップ達成率バー**（v2.10.0 追加、ステップが 1 件以上ある場合のみ表示。バッジは廃止せずバーを追加表示。このステップ達成率バーはカンバンビューの子タスクカードのみに表示し、テーブル・カレンダー・タイムラインには表示しない）を表示。
- 親タスク追加ボタンは各カラムヘッダーの「＋」ボタンに統一されている（v2.7.0 で画面上部の共通「親タスク追加」ボタンを廃止した経緯がある）。
- 親タスクの並び順は`sortGroupsByCreatedAtDesc()`（作成日時の新しい順、v2.8.0 導入。カンバンビュー自体は API 取得順＝`sort_order ASC, id ASC`をそのまま使い、この並び替え関数はテーブルビュー専用である点に注意 — 現行コードの`renderKanban()`も API 取得順をそのまま使用）。
- 描画方針：カンバン全体は「データから盤面をまるごと作り直す」1 本の描画関数（`renderKanban()`）で再構築し、親の所属列は保存せず毎回子のステータスから算出する。再描画時は開いているアコーディオンの開閉状態（`expandedGroupIds`）を事前に記録し、再描画後に復元する。

#### 2.2 テーブル表示

- 「未着手」「進行中」「完了」の 3 ステータス大枠に分け、各枠はクリックで折りたたみ可能（開閉状態は`localStorage`の`collapsedTableStatuses`に保存）。
- 各枠の中に親タスク（グループ）行をアコーディオン形式で表示し、クリックで子タスク行の表示/非表示を切り替え（`collapsedTableGroups`に保存）。親タスク行には子タスク追加ボタン（＋）と編集ボタンを配置。
- 子タスク行の列構成：
  |カラム名 |種別 |説明 |
  |:--------- |:--------- |:--------------------------------------------|
  |タイトル |テキスト |タスクの名称 |
  |種別 |タグ |「本」「YouTube」などのタスク種別バッジ＋カテゴリバッジ|
  |ステータス |ステータス |未着手 / 進行中 / 完了 のドット＋テキスト |
  |進捗率 |バー |紐づくステップの完了率（%） |
  |予定日 |日付 |開始予定日 |
  |完了日 |日付 |終了日（実績） |
  |学習時間 |数値 |実績学習時間（h） |
  |ステップ |分数 |達成ステップ数 / 全ステップ数（例：2/4） |

- 最下部にインライン親タスク追加行（テキスト入力＋保存ボタン）を配置し、その場で新規`groups`を POST できる。
- **進捗率カラム**（v2.10.0 追加）：グループ行はそのグループの子タスク完了数/全体数（%）をバー＋ラベルで表示（0 件は「－」）。子タスク行は当初 v2.10.0 では紐づくステップの達成数/全体数（%）を表示していたが、**v2.16.0 でステップ達成率ベースに統一**されている（現行コードもステップの完了数/全体数に基づく`table-progress`バーで表示。ステップ 0 件のタスクは 0%バー表示）。

##### 進捗率カラム新設に伴う不具合修正の経緯（v2.10.1）

進捗率バー実装直後、カンバンビューの親カードをクリックしても子タスク一覧が開閉しなくなる不具合が発生した経緯がある（アコーディオン開閉の DOM 順依存が原因。現行実装では解消済み）。

#### 2.3 カレンダー表示

- 月表示のカレンダー形式（42 マス＝ 6 週固定でレンダリング、月の最終週が翌月にはみ出さない場合は 6 週目を省略）。
- 表示モードは「すべて／予定／実績」の 3 トグル（`localStorage`の`calendar_display_mode`に保存）。
- 各週の内部にタスクバーを絶対配置し、レーン計算により同一週内で重ならないよう縦に積み上げる。予定バー（半透明ホワイト）と実績バー（アンバー系、「実」ラベル付き）を、モードに応じて表示/非表示。
- セルの空きスペースをクリックすると、その日付を初期値としたグループ選択モーダル → タスク登録モーダルを開く（子タスク追加）。バークリックでタスク編集モーダルを開く。
- 表示中の年月は`localStorage`の`calendar_selected_year`/`calendar_selected_month`に保存し、次回表示時に復元。

#### 2.4 タイムライン（ガントチャート）表示

- 左側にグループ名（200px 固定幅）、右側に日付軸（1 日〜月末日）とバーを配置した 2 カラムグリッド構成のガントチャート形式。1 行目は日付軸専用の行。月単位でナビゲーション（前月/次月ボタン、月ピッカー入力）。
- バーはドラッグ＆ドロップで日付を移動可能（`start_planned_date`を更新）。バー両端のリサイズハンドルで開始日・終了日を個別に調整可能（`updateTaskDuration()`で PUT）。
- 親タスクの並び順は`sortGroupsByEarliestPlannedDate()`（子タスクの最も早い予定開始日順、日付未設定のグループは ID 順で末尾に）。子タスクが 0 件のグループも表示対象（ステータス判定上は「未着手」に分類される）。
- 空きトラッククリックでその日付を初期値とした子タスク追加（親タスクが特定できる場合はそのまま、できない場合はグループ選択モーダル経由）。

##### ステータス絞り込みタブ（すべて/未着手/進行中/完了）（v2.21.0：ステータス大枠分割から単一選択タブ方式に変更）

- **v2.20.0 時点の原仕様**：親グループを未着手/進行中/完了の 3 大枠（`.timeline-status-header-row`）に分けて表示し、▾/▸ で開閉可能にしていた（`localStorage: collapsedTimelineStatuses`）。判定は既存の`calcStatus()`を使用。
- **v2.21.0 での変更理由**：この「3 大枠を常時並べて個別に開閉する」方式はテーブルビューと見た目が似すぎており、タイムライン本来の「時系列で見る」目的と噛み合わず使用感が悪かったため廃止。代わりに、カレンダービュー・表示モードタブと同じ「単一選択のタブで絞り込む」方式に統一した。
- **現行仕様**：タイムラインツールバー（`.timeline-toolbar`）左側に「すべて／未着手／進行中／完了」タブ（`.timeline-status-filter-tab`。v2.21.15 でクラス名を`timeline-status-tab`から統一）を配置し、単一選択で該当ステータスの親グループのみ表示する。各グループの属するステータス判定は既存の`calcStatus(groupId, tasks)`（テーブル・カンバンと同一ロジック）。選択状態は`localStorage`（キー：`timeline_status_filter`）で保持しリロード後も復元。絞り込み後の並び順は`sortGroupsByEarliestPlannedDate()`を適用。該当グループが 1 件もない場合は「該当するタスクがありません」と表示。この変更に伴い、v2.20.0 のステータス大枠見出し行・開閉状態（`collapsedTimelineStatuses`）は廃止。
- **「完了タスクを非表示」チェックボックスの廃止（v2.20.1〜v2.21.0 で完全撤去）**：v2.20.1 でステータス大枠の開閉機能と完全に重複するため機能的に無効化し（「完了」大枠を折りたためば同じ結果が得られ、かつ開閉状態が永続化される点で上位互換だったため）、v2.21.0 でコードごと完全に削除した。完了タスクのみ見たい場合は「完了」タブを選択する。

##### グループ行ごとの ▼ トグル（子タスクバーの表示/非表示）（v2.20.0 追加）

テーブルビューのグループ行折りたたみと同じ考え方で、各グループ行の左側に ▼/▸ トグルボタン（`.timeline-group-toggle`）を持つ。クリックでそのグループの子タスクバー（予定バー・実績バー）の表示/非表示を切り替える。折りたたみ時はトラックの高さを最小（40px）に圧縮し、バー・本日ラインとも描画しない（v2.21.2 で、折りたたみ時にバー自体を生成しない方式に修正。それ以前はトラック高さのみ圧縮しバーの HTML 自体は生成されたままだったため、圧縮された高さからバーがはみ出して隣接行と重なって見える不具合があった）。開閉状態は`localStorage`（キー：`collapsedTimelineGroups`）で保持。グループ行ヘッダーは「グループ名（子タスク件数）」形式で表示。

##### 表示モード切替タブ（すべて/予定/実績）（v2.20.0 追加）

カレンダービューと同じ「すべて／予定／実績」の表示切替タブ（`.timeline-mode-tab`）をツールバー右側に配置する。すべて（デフォルト）＝予定バー（上段）・実績バー（下段）を両方表示、予定＝予定バーのみ、実績＝実績バーのみ（`start_date`設定タスクのみ対象、上段位置に描画）。選択状態は`localStorage`（キー：`timeline_display_mode`）で保持。1 タスクあたりの行占有高さは「すべて」時 48px 固定、「予定」または「実績」単独表示時は 26px に圧縮。

- **レーン割り当ての一本化（v2.21.2）**：予定バーのレーン間隔（24px 固定）と「すべて」モード時の実績バーのレーン間隔（48px）が異なるスケールで独立計算されていたため、トラック高さの算出根拠（24px 基準）と実際のバー配置（48px 基準）が食い違い、レーン数の多いグループでバーが次の行に溢れる不具合があった。1 タスク＝ 1 レーンとし、レーン高さ（`LANE_HEIGHT`）を表示モードに応じた単一の値（すべて：48px／単独：24px）に統一し解消した。

##### 予定・実績バーの配色方針の変遷（v2.21.3→v2.21.4）

- **v2.21.3**：従来の配色（予定＝紫、実績＝オレンジ）が、ダッシュボードの日別学習時間グラフの配色（予定＝オレンジ、実績＝紫）と正反対で紛らわしいという指摘を受け、予定＝アクセントカラーのインディゴ系、実績＝完了ステータスの緑系に変更。カレンダー・タイムライン両ビューに同じ配色を適用（ダッシュボードのグラフ配色は変更せず）。
- **v2.21.4（現行）**：「すべて」モードで多数のバーが重なりテキストが省略表示になると、色が 2 色しかないため科目の判別が全くできないという指摘を受け、`getCategoryChartColor()`（ダッシュボードのカテゴリ別グラフ・カンバン/テーブルのカテゴリバッジと共通の関数）を使った科目（カテゴリ）ごとの色分けに変更。予定バーは薄め（背景不透明度 0.28、枠線 0.55）、実績バーは濃いめ（背景不透明度 0.55、枠線 0.85、文字白）の不透明度で表示し、予定/実績の区別は色ではなく縦位置（予定が上段、実績はその 22px 下または単独モード時は同位置）で行う。カレンダービューの実績バーには従来通り「実」の接頭テキストも表示する。`tasks.css`の`.timeline-bar--planned`/`--actual`・`.calendar-task-bar--planned`/`--actual`からは色指定を削除し構造のみを定義。実際の色は`tasks.js`側でタスクごとに`getCategoryChartColor(task.category_name)`を計算しインライン style で指定する。

##### 不具合修正の経緯（v2.21.0・v2.21.1）

- **v2.21.0**：(1) 実績バーが常に表示されないバグ（`task.start_actual_date`という存在しないフィールド名を参照していたのを`task.start_date`に修正）。(2) 本日ラインが行をまたいでページ全体に伸びる不具合（`.timeline-track`への`position: static !important`強制指定の副作用を解消し`position: relative`を維持するよう修正）。(3) 日付軸行の空きスペースクリックがグループ追加ピッカーを誤って開く不具合（`.timeline-row-header--axis`セレクタが実 DOM に付与されておらず除外判定が機能していなかったのを修正）。
- **v2.21.1（スクロール方式の統一）**：v2.21.0 時点では`.timeline-wrapper`を「ページ全体をスクロールさせる」方式（`height: auto; overflow-y: visible;`）にしていたが、この方式では`.timeline-toolbar`・日付軸行の sticky 計算基準がページの他の sticky 要素（`.tasks-header`・`.view-tabs`）と異なってしまい、要素同士が重なって表示が崩れる不具合が発生した。テーブルビュー・カンバンビューと同じ「高さ固定（`height: 65vh`）＋内側だけでスクロール（`overflow: auto`）」方式に統一して解消。日付軸行（`.timeline-row--axis`）はテーブルビューの`<thead>`と同じく`.timeline-wrapper`自身を基準にした`top: 0`に変更。`.view-panel[data-view-panel="timeline"]`のみ`overflow: visible`の例外指定を持つ。

#### ビューコンテナの高さ算出（v2.21.11 追加）

- `syncTaskViewHeights()`が、ヘッダー（`.tasks-header`）と閲覧タブ（`.view-tabs`）の実測高さから、画面に収まる利用可能 px（`window.innerHeight - headerHeight - viewTabsHeight - 32px`、最低 300px）を算出し、カンバン・テーブル・タイムラインの各コンテナ高さに動的適用する。タイムラインはさらにツールバー高さ分を差し引く。
- `renderTaskViews()`・`switchView()`・`renderTimeline()`・`window`の`resize`イベントから呼び出される。

#### タイムラインの sticky 追従ヘッダー（v2.21.0 追加・v2.21.1 で方式変更）

- `syncTimelineStickyOffsets()`が`.view-tabs`の CSS 計算上の`top`値と実測高さから`.timeline-toolbar`の`top`値を動的に算出し、スクロール時にビュータブのすぐ下へ追従して固定表示されるようにする。

#### タイムラインビュー：ステータス絞り込みタブのクラス名不一致修正（v2.21.15）

タイムラインビュー右上の「すべて／未着手／進行中／完了」ステータス絞り込みタブについて、実装ファイル間でクラス名・data 属性名が食い違っており、クリックしても絞り込みが機能しない不具合があった。並行して作業していた別の AI ツール（Gemini）のセッションで`index.html`側のクラス名・data 属性名が変更されたものの、`tasks.js`側の参照が追随していなかったことが原因。

- **正しい実装（`index.html`基準に統一）**：
  - クラス名：`timeline-status-filter-tab`（誤：`timeline-status-tab`）
  - data 属性名：`data-status-filter`（誤：`data-status`）
- `tasks.js`内の以下 2 箇所を、上記のクラス名・data 属性名に合わせて修正した。
  - `renderTimeline()`内：現在の絞り込み状態に応じて`active`クラスを付与する処理
  - タブのクリックイベント登録処理（`localStorage`への保存と`renderTimeline()`の再実行）
- `tasks.css`側は同時期の修正で先に`timeline-status-filter-tab`に統一済みだったため、見た目（左側の「すべて／予定／実績」タブとのデザイン統一）は正しく反映されていたが、JS 側のクラス名不一致によりクリック操作自体が機能していなかった。
- `localStorage`のキー名自体（`timeline_status_filter`）は変更していない。今回修正したのは、このキーに保存する値を参照・比較する側（DOM 要素のクラス名／data 属性名）のみである。
- 今後、複数の AI ツール（Claude／Gemini 等）を並行利用する際は、HTML・CSS・JS の 3 ファイル間でクラス名・data 属性名の変更が全て反映されているかをセッション開始時に確認することとする（詳細は本文書末尾「アプローチ・パターン」を参照）。

### ④ 書籍マスタ画面

#### 4.1 検索・登録

- Google Books API を利用した書籍検索（`book-search-input`＋「検索」ボタン）。`https://www.googleapis.com/books/v1/volumes`に対し`langRestrict=ja`・API キー（`config.js`の`GOOGLE_BOOKS_API_KEY`）を付与してリクエストし、最大 5 件の候補（タイトル・著者・表紙サムネイル）を表示。各候補に「登録」ボタンがあり、クリックで`POST /api/books`（`title`/`author`/`cover_url`）を実行して登録する。
- 登録完了後は検索入力欄・検索結果・絞り込み入力欄をすべてクリアする（v2.21.5）。

#### 4.2 一覧表示（v2.17.0：カンバン形式に変更）

- 「未読／読書中／読了」の 3 ステータスを、タスク一覧のカンバンビューと同様の 3 カラム形式で表示する（v2.17.0）。従来のグリッド表示（`#book-list`）を廃止し、`.kanban`/`.kanban-column`/`.kanban-cards`等、タスクカンバンと共通の CSS クラス（`tasks.css`）を流用する（新規 CSS ファイルは追加しない）。その後 v2.21.6 で、3 カラムを**横並びから縦積み**（各ステータスがセクションとして上から順に並ぶ）表示に変更し、各セクション内で書籍カードをグリッド表示（`repeat(auto-fill, minmax(280px, 1fr))`で自動折り返し）するよう改めている。各ステータスセクション（v2.21.6 以降）／各カラム（v2.17.0 時点）のヘッダークリックで開閉可能。
- ステータス判定（`calcBookStatus()`、v2.17.0 追加）：**DB にステータス用カラムは追加せず**、`books`テーブルの`total_chapters`/`completed_count`および紐づく子タスクの`status`から、表示のたびにフロントエンドで自動算出する。判定優先順位：
  1. **読了**：`total_chapters`が設定済み、かつ`completed_count >= total_chapters`
  2. **未読**：紐づく子タスクが 0 件、または全ての子タスクが「未着手」
  3. **読書中**：上記いずれにも該当しない場合（子タスクが 1 件でも「進行中」または「完了」を含む）
- 進捗表示：「進捗 N%（完了数 / 全何章）」の形式。進捗率は紐づく子タスクのうち「完了」の件数を`total_chapters`で割って算出し、**`Math.min(100, ...)`で 100%を上限にクリップする**（1 章に複数タスクを紐づけた場合に完了数が章数を超えても表示上は 100%止まりにするため）。`total_chapters`が未設定の書籍は進捗バー・進捗率を表示しない。
- 各カラム（縦積みセクション）のヘッダーには件数バッジを表示。色分けはタスクカンバンの未着手（グレー）/進行中（インディゴ）/完了（グリーン）のドット配色をそのまま流用（未読＝ todo、読書中＝ inprogress、読了＝ done）。
- **並び替え・ドラッグ＆ドロップは非対応**（v2.17.0 導入時からの仕様）。ステータスは子タスクの状態から自動算出されるため、カードを別カラム/セクションへドラッグしても永続化されない。
- 書籍カード：表紙画像（未設定時はプレースホルダー）、タイトル、著者名、（レガシーの）メモ、`total_chapters`設定時は進捗バーを表示。
- 「登録済みの書籍を絞り込む…」入力でタイトル・著者名に対するクライアントサイドのリアルタイムフィルタリングが可能。

#### 4.3 書籍詳細・編集ダイアログ（v2.21.9：表示項目を拡張／v2.21.8：右サイドパネル化／v2.21.14：メモ機能の実装単位を訂正）

画面右端からスライドインする右サイドパネル形式（幅 800px・最大 92vw、画面右からのスライドインアニメーション）で表示。

| 項目                     | 種別                 | 入力ルール / 説明                                                                                                                                                                    |

| 表紙画像                 | 画像                 | `cover_url`を表示。未設定時は「表紙」のプレースホルダーを表示                                                                                                                        |
| 書籍タイトル             | ヘッダーテキスト     | 表紙の隣に表示（編集不可。Google Books 登録時の値をそのまま表示）                                                                                                                    |

### ⑦ リザルト画面（v2.16.0 追加・GitHub Issue 発端の機能）

週次／月次／年次の学習サマリーを振り返るレポート画面。期間の境界（週初め・月初め・年初め）に前期間のリザルトを自動ポップアップ表示する機能も備える。サイドバーのメインナビに「リザルト」リンク（Lucide アイコン：`trophy`）があり、ルーティングは`#page-results`。`resultsInitialized`フラグで初回のみ`initResults()`を実行し、2 回目以降は現在アクティブなフィルタータブに合わせてカードの表示状態を復元する。

#### 7.1 自動ポップアップ

- アプリ起動時（`app.js`末尾）に`checkAndShowResultPopup()`を 800ms 遅延で実行する。
- 以下の条件を満たす場合にポップアップを表示する：
  - **今日が月曜日**（`day === 1`）かつ先週のリザルトが未表示
  - **今日が 1 日**（`date === 1`）かつ先月のリザルトが未表示
  - **今日が 1 月 1 日**（`month === 1 && date === 1`）かつ昨年のリザルトが未表示
- 表示済みかどうかは`localStorage`（キー：`shownResults`、値：表示済み ID の配列 JSON）で管理する。
- 複数のリザルトが保留中の場合は、スライドナビゲーション（`result-modal-nav`）で前へ/次へ切り替え可能。
- 「リザルトページで見る」ボタン（`btn-result-modal-go-page`）で`#page-results`に遷移してモーダルを閉じる。モーダルを閉じると全保留リザルトを表示済みとしてマークする（`markResultShown()`）。

#### 7.2 生成する期間リスト（`generatePastPeriods()`）の変遷

- **v2.16.0 時点の原仕様**：週次＝直近 4 週分（今週分は含めない）、月次＝直近 3 ヶ月分、年次＝昨年 1 年間（1/1〜12/31）。
- **現行実装（v2.21.14 時点）**：週次 4 件・月次 12 ヶ月分・年次 2 年分に加え、現在進行中の期間（今週・今月・今年、`isCurrent: true`）のカードも先頭付近に含めるよう拡張されている（詳細は 7.3 節）。この拡張がいつ行われたかは、v2.19.0 と v2.21.13 の間の未入手期間にあたるため経緯不明。

#### 7.3 カード内容（モーダル・ページ共通）

各カードは開閉可能なアコーディオン（`<details>`）形式で、以下を含む（`buildResultContent()`）：

- ヘッダー：期間タイプバッジ（週次/月次/年次、週＝インディゴ系／月＝アンバー系／年＝グリーン系）＋期間ラベル（例：「6/8 〜 6/14」「2026 年 5 月」）
- 比較ラベル：「前週との比較」「前月との比較」「前年との比較」（前期データが存在する場合のみ表示）
- 統計 3 枚：学習時間（h）・完了タスク（件）・進捗率（期間内、%）。各カードに前期との差分バッジ（`result-diff`、`buildDiffBadgeHtml()`）を表示：
  - UP（増加）：アンバー系・上矢印アイコン・クラス`result-diff--up`
  - DOWN（減少）：青系・下矢印アイコン・クラス`result-diff--down`
  - STAY（変化なし）：緑系・横線アイコン・クラス`result-diff--stay`
  - 表示フォーマットは`±N（単位）`。数値カード・差分バッジともにフェードイン＋バウンスアニメーション付き（`.result-stat-value--anim`→`.result-stat-value--visible`の`statFadeIn`キーフレーム、`.result-diff--visible`の`diffFadeIn`＋アイコンバウンス`bounceUp`/`bounceDown`）
- グラフ 2 枚：カテゴリ別学習時間（縦棒）・ステータス別件数（ドーナツ）。カード（モーダル含む）ごとに個別の canvas id を割り当て、Chart.js インスタンスの衝突を防止する。モーダル用は`modalChartBar`/`modalChartDoughnut`として、スライド切り替え時に`destroy()`で先に破棄してから再生成する（重複エラー防止。ダッシュボードの`upsertChart()`方式とは異なる、リザルト画面独自の管理方式）。
- 期間内タスクの絞り込みロジック（`filterTasksByPeriod()`）：`status === '完了'`のタスクは`end_date`を基準日、それ以外は`end_planned_date`または`start_planned_date`を基準日として判定し、基準日が期間範囲内に入るタスクを対象とする。

#### 7.4 振り返り機能（目標・実績・よかった点・反省点・備考）（v2.18.0 追加・GitHub Issue #51 対応）

学習データから自動集計される数値（学習時間・完了タスク数等）とは別に、ユーザーが定性的に書き残す振り返りを各リザルトカード（週次・月次・年次）に付与する機能。週次・月次・年次のいずれも同一の 5 項目＋気分アイコンで統一する。

| 項目       | 入力形式           | 説明                                     |
| ---------- | ------------------ | ---------------------------------------- |
| 目標       | テキストエリア     | その期間の目標                           |
| 実績       | テキストエリア     | 自動集計とは別に手書きで書く実績の要約   |
| よかった点 | テキストエリア     | うまくいったこと                         |
| 反省点     | テキストエリア     | 改善したいこと                           |
| 備考       | テキストエリア     | 自由記述                                 |
| 気分       | 絵文字選択（5 種） | 😄／🙂／😐／😣／😢 から 1 つ選択（任意） |

- 「保存」ボタン（`.btn-review-save`）クリックで`POST /api/result-reviews`に即時保存する（モーダルの開閉・他の保存処理とは独立）。保存処理はリザルトページ・リザルトポップアップモーダルの両方に同一ロジックで適用する。保存済みの振り返りがある期間はテキストエリアに既存値を初期表示し、上書き保存できる（同一期間キーでの再保存は更新扱い）。
- **期間との紐付け（データの一意性）**：`result_reviews`テーブルの`period_type`（week/month/year）＋`start_date`＋`end_date`の組み合わせで一意に特定する（UNIQUE KEY）。`POST /api/result-reviews`は対象期間キーが既存なら UPDATE、なければ INSERT する（`ON DUPLICATE KEY UPDATE`による upsert）。
- **月次・年次における参考表示**：月次カードはその月に含まれる週次振り返り、年次カードはその年に含まれる月次振り返りの「目標」「よかった点」「反省点」を`<details>`アコーディオン（デフォルト閉じた状態）で抜粋表示する。**あくまで閲覧用の参考表示であり、自動集約・自動転記は行わない**（5 項目のデータは週・月・年それぞれ独立して保存される）。該当する子期間の振り返りが 1 件もない場合はアコーディオン自体を表示しない。
- **データ取得・キャッシュ**：`reviewsCache`（配列）に`GET /api/result-reviews`（全件）の結果を保持する。`initResults()`・`checkAndShowResultPopup()`の冒頭でそれぞれ`loadReviewsCache()`を呼び全件を取得する（リザルトページ・ポップアップモーダルそれぞれ独立してロード）。保存成功時は`reviewsCache`内の該当レコードを API レスポンスで即時更新し、再フェッチなしで画面に反映する。

#### 7.5 「今週」「今月」「今年」の進行中カード（v2.21.14：ドキュメント反映）

`generatePastPeriods()`（`results.js`）は、v2.16.0 原仕様の過去の確定済み期間（週 4 件・月 12 ヶ月分・年 2 年分、後述の通り月・年の件数は v2.16.0 原仕様の 3 ヶ月分/1 年分から拡張されている）に加えて、**現在進行中の期間（今週・今月・今年）のカードも先頭付近に含める**実装になっている。この仕様自体は実装済みだったが、要件定義書への反映が漏れていたため、v2.21.14 で追記された。

- 「今週」：`id: "week-page-current"`、月曜〜日曜の範囲、`isCurrent: true`
- 「今月」：`id: "month-page-current"`、月初〜月末の範囲、`isCurrent: true`
- 「今年」：`id: "year-page-current"`、1/1〜12/31 の範囲、`isCurrent: true`
- いずれも進行中の期間のタスク・振り返りをその場で確認・入力できるようにする目的のカードであり、期間が終了した後は通常の「N 週間前」「N ヶ月前」等のカードと同様に扱われる。

#### 7.6 フィルタータブ

- ページ画面上部に「週／月／年／全」のタブがあり、`.result-page-card`のクラス（`result-type-week`等）に応じて表示/非表示を切り替える。初期表示は「週」のみ。

### ルーティング

- SPA 的なルーティング：サーバー側は`app.get("/{*path}", ...)`で未定義パスはすべて`index.html`を返す。
- 画面遷移はハッシュベース（`location.hash`）で行い、`app.js`の`showPage()`がハッシュ変更を監視して該当`<section>`の表示切替・各画面の初回初期化（`initBooks()`/`initDashboard()`/`initSettings()`/`initMandala()`/`initResults()`）を行う。各画面の初期化はフラグ変数（`booksInitialized`等）で一度だけ実行され、2 回目以降の表示では最新データの再取得・再描画のみ行う。
- **既知の障害パターン（v2.16.0 で明文化）**：各`initXxx()`内で`document.getElementById(...).addEventListener(...)`のように要素取得直後にイベント登録する箇所がある場合、対応する HTML 要素が`index.html`に存在しないと`showPage()`全体が例外で中断し、以後すべてのページ遷移ができなくなる（特定ページでリロード → 他ページへ遷移できなくなる不具合の典型例）。フラグ変数名は宣言時と設定時で一致させ、要素取得後にイベント登録する際は要素の存在確認、または対応要素が`index.html`に必ず存在することを確認する運用を徹底する。

### データ型・日付処理の統一

- 親タスク・子タスク・書籍・マスタテーブルの ID はすべて`INT UNSIGNED`（number）で統一する。
- 日付フィールド（`start_planned_date`・`end_planned_date`・`start_date`・`end_date`等）は DB の型を`DATE`（YYYY-MM-DD）とする。
- 日付比較・表示は`getFullYear()`/`getMonth()`/`getDate()`をベースにローカル日付として扱い、`slice(0,10)`のような文字列切り出しは避ける（UTC 格納によるオフセットバグを回避するため確立した方針）。
- 学習時間は DB 上は分単位（`SMALLINT UNSIGNED`）で保存し、UI 表示・入力は時間（h、小数点 1 桁）で行う。変換は`minutesToHours()`（各 JS ファイルに個別定義）で統一。保存時は`Math.round(parseFloat(入力値) * 60)`で分に変換する。

### ライト/ダークモード

- CSS 変数（`--color-bg-base`等）を`:root`と`html.light`の 2 セットで定義し、`documentElement`への`light`クラス付与/除去のみで全体の配色を切り替える。

### モーダルの実装方針

- HTML に事前記述・JS で表示/非表示を切り替える方式（`.modal.hidden { display: none; }`でオーバーレイの`display: flex`を上書き）。
- `.modal`は`z-index: 1000`で固定。`app.js`がページ見出し（`.tasks-header`等）に動的付与する`z-index: 999 !important`より必ず手前に来るよう、モーダルの z-index をそれより高く設定する方針が確立している（タイムラインのバー等より手前に表示するため元々明示指定していたものを、v2.21.10 でさらに引き上げた経緯がある）。
- **ステップの即時保存と未保存確認ダイアログの関係**：ステップ（孫タスク）の追加・チェック・削除・日付/時間編集はすべて即時 API 通信で確定し、モーダルの「保存」「キャンセル」「✕」ボタンはステップへの変更に影響しない。そのため、ステップのみを変更してモーダルをキャンセルで閉じても、ステップの変更は元に戻らない（既知の仕様）。モーダルの Dirty 判定のスナップショットにはステップ情報も含まれているため、ステップだけを変更してキャンセルした場合でも未保存確認ダイアログが表示されることがある（既知の挙動として許容）。
- 未保存確認（タスクモーダル・グループモーダル）：`markXxxModalClean()`（モーダルを開いた直後・保存/削除成功直後に呼び、現在のフォーム値を`dataset.initialSnapshot`に JSON 文字列として保存）→`isXxxModalDirty()`（現在値とスナップショットを比較）→`closeXxxModalWithConfirm()`（dirty な場合のみ確認ダイアログを表示）という 3 関数の組み合わせで実現する。

### カンバンの描画方針

- 「データから盤面をまるごと作り直す」描画関数（`renderKanban()`）を 1 本用意し、親の所属列は保存せず毎回子のステータス配列から算出する。
- カンバン全体の再描画時、開いているアコーディオンの開閉状態（`expandedGroupIds`）を再描画前に記録し、再描画後に復元する。
- カンバン上の親カードの並び順は`groups`の API 取得順（`sort_order ASC, id ASC`）をそのまま使用する（後述のグループ並び替え関数の対象外）。

#### `calcStatus`の完了判定ロジック（v2.3.0 で確立）

```javascript
function calcStatus(groupId, tasks) {
  const children = tasks.filter((t) => t.group_id === groupId);
  if (children.length === 0) return "未着手";

  const currentYear = new Date().getFullYear();
  const completedThisYear = (t) =>
    t.status === "完了" &&
    t.end_date &&
    new Date(t.end_date).getFullYear() === currentYear;

  if (children.every(completedThisYear)) return "完了";
  if (children.every((t) => t.status === "未着手")) return "未着手";
  return "進行中";
}
```

### 進捗率バー（v2.10.0 追加）

#### 親グループの進捗率（`calcGroupProgress`）

算出基準：その親グループに属する子タスクの完了数/全体数（%）。子タスクが 0 件の親グループは`null`を返し、表示側は「－」とする。

```javascript
function calcGroupProgress(groupId, tasks) {
  const children = tasks.filter((t) => t.group_id === groupId);
  if (children.length === 0) return null;
  const completed = children.filter((t) => t.status === "完了").length;
  return Math.round((completed / children.length) * 100);
}
```

カンバンでは親カードのヘッダー直下に、テーブルではグループ行の進捗率カラムに、それぞれバー＋ラベルで表示する。

#### カンバン子タスクカードのステップ達成率バー

算出基準：そのタスクに紐づくステップの達成数/全体数（%）。ステップが 0 件のタスクはバーを表示しない。「◯/◯ ステップ完了」バッジとは独立して追加表示される（カンバンビューの子タスクカードのみに表示）。

```javascript
function createStepProgressBarHtml(steps) {
  if (!steps || steps.length === 0) return "";
  const completed = steps.filter((s) => s.is_completed).length;
  const percent = Math.round((completed / steps.length) * 100);
  return `<div class="task-card-step-progress"><i style="width:${percent}%"></i></div>`;
}
```

### グループの並び替え（v2.8.0 追加）

ビューごとに異なる並び順を要求するため、`groups`配列をそのまま描画に使わず、ビュー固有のソート関数を経由してから描画する。**ソートはフロントエンド側で行い、API（`GET /api/groups`）の返却順は変更しない**（カンバンビューが既存の取得順に依存しているため）。

#### `sortGroupsByCreatedAtDesc(groups)` — テーブルビュー用

作成日時の新しい順（新規作成したグループが一番上）。`renderTable()`から呼び出される。

#### `sortGroupsByEarliestPlannedDate(groups, tasks)` — タイムラインビュー用

子タスクの`start_planned_date`のうち最も早い日付の昇順（古い予定日のグループが一番上）。日付を持つ子タスクが 1 件もないグループ（子タスク 0 件を含む）は、日付を持つグループ群の末尾に ID 昇順で配置する。`renderTimeline()`から呼び出される。完了タスク非表示フィルタの ON/OFF に関わらず、並び替えの基準は全子タスク（フィルタ前）の`start_planned_date`を用いる。

### ダッシュボードの期間範囲算出（v2.21.7 追加・v2.21.13 で用途を見直し）

- `getPeriodRange(period, baseDate)`（`dashboard.js`）：`week` / `month` / `year`を受け取り、`baseDate`を基準にその期間の開始日時・終了日時（`{ start, end }`）を返す共通関数。`all`は`null`を返す。この関数自体の算出ロジックは v2.21.7 から変更していない。
  - `week`：`baseDate`を含む週の月曜 0:00〜日曜 23:59:59
  - `month`：`baseDate`の月の 1 日 0:00〜末日 23:59:59
  - `year`：`baseDate`の年の 1/1 0:00〜12/31 23:59:59
- `getCurrentPeriodRange(period)`：`getPeriodRange(period, viewDate)`を呼ぶラッパー。目標設定モーダル（`openGoalModal()`）・目標表示（`loadAndShowCurrentPeriodGoal()`）はこれまで通りこの関数を呼び出す（呼び出し側の実装変更なし）。
- **v2.21.13 での用途変更**：進捗率カードの締め日時（`borderDate`）算出への使用は廃止した。現在`getPeriodRange()`は、(1) 目標設定モーダル・目標表示の期間範囲算出、(2) 進捗率カードの前期間比較で「1 つ前の期間の日付範囲」を算出する用途、の 2 つに使われている。以前のように「現在時刻でキャップする」処理（`borderDate` / `prevBorderDate`）は進捗率カードの算出からは無くなった。

## アプローチ・パターン（複数 AI ツール併用時の確認事項）

（v2.21.15 で正式に明文化。以前から確立していた運用上の注意点を要件定義書に明記したもの）

- 本プロジェクトは Claude（Cursor 経由）と Gemini（別セッション）を並行利用して開発を進めているため、一方のツールでの HTML/CSS/JS いずれかの変更が、もう一方のツールの認識（ナレッジ・会話履歴）に反映されないまま作業が進むことがある。
- 特にクラス名・data 属性名・id 名は、HTML／CSS／JS の 3 ファイルすべてで一致している必要があるため、UI の見た目やクリック操作に不具合が出た際は、まずブラウザの開発者ツールで実際の HTML 要素（`class`・`data-*`属性の実際の値）を確認し、CSS・JS 側の参照名と食い違っていないかを最初に疑う。
- セッション開始時は、要件定義書の記載だけでなく実ファイル（特に関連する HTML/CSS/JS の 3 点セット）を確認し、クラス名・属性名の差分を検出してから作業に入る（既存の「コードと要件定義書の同期」の原則に加え、実装ファイル間の同期確認も明示的に行う）。
